# 运行、资源与数据迁移

状态：部署设计基线，当前没有已安装服务或运行数据库。架构来源见[架构规范](architecture.md)。

## 默认部署

**默认采用宿主机 Node + systemd，与 newbd 的部署类型一致。** 首期不维护 Docker/Compose 部署入口；以后有跨机器交付或容器隔离需求时，再增加单应用容器方案。

- 新服务名为 newfc.service，具有独立 WorkingDirectory、环境配置、日志和运行身份；不修改或复用 newbd-budget.service。
- systemd 负责开机启动、进程异常重启和 journald 日志。运行编译后的 JavaScript，日常运行不启动 Vite dev server、ts-node 或额外进程管理器。
- Express 提供前端静态产物、业务 API 和 SSE；应用监听独立的本机端口。需要域名/HTTPS 时使用宿主已有 Nginx 的独立站点配置，正确配置流式响应和可信代理跳数。
- SQLite、附件与备份使用独立持久目录，更新代码和替换构建产物不覆盖这些目录。备份仍按数据库与文件一致性规则执行。
- 固定兼容的 Node 版本与锁文件，better-sqlite3 的安装、构建和运行使用匹配的 Node ABI；不共用 newbd 的 node_modules。
- 部署流程为新目录内安装锁定依赖、测试、构建、必要的数据备份/显式迁移，再替换新应用产物并重启新服务。构建失败不替换运行产物；普通进程重启不触发安装或重新构建。测试构建输出也与正在服务的产物分离。
- 初始数据库创建和后续迁移使用明确的部署步骤；代码回退涉及数据库变更时，按已验证的兼容性或恢复方案处理。

主要资源收益来自减少 MySQL、MinIO、Redis、worker 等常驻服务，而非取消容器本身。单容器同样可以很轻；当前采用 systemd 是为了沿用已熟悉的运维方式，并保持部署规模简单。实际内存目标以本文件规定的工作负载测量结果为准。

## 运行配置边界

实例至少要明确应用根目录、监听地址/端口、SQLite 路径、文件/临时/备份目录、会话配置和模型配置。优先沿用并收口 newbd 配置，不为每个功能新增开关。确切键名在导入源码后登记，不能提前声称已有 .env.example。

存活检查判断进程是否运行；就绪检查确认本实例数据库 schema 和所需存储可用。模型未配置不得阻止预算等确定性业务就绪。停止服务时停止领取新任务、结束或标记中断任务、关闭数据库连接；超时强停后启动恢复逻辑识别未完成任务。

临时上传、导出、模型日志和备份都要设保留/清理策略；清理只能触及本实例目录，不删除仍被业务引用的不可变证据。限额在相应任务实测后固定。

## 运行数据迁入与恢复

- **开发启动**：使用新建空库及可丢弃测试样本，独立运行；不以是否迁入旧运行库作为阶段 0 的前提。
- **实际迁入前**：确认应保留的 newbd/lishui 历史版本、导入批次、原始附件、审批、审计与会话范围。未确认保留范围不自动丢弃，也不盲目全量导入。
- **单向导入**：固定源快照，生成源 ID 到目标 ID 的映射和文件哈希清单，在新库试导入；导入可重跑且重复执行不增加事实，原系统保持只读来源角色。
- **核对**：按组织、期间和业务类型检查记录数量、金额/数量汇总、版本状态、外键与文件可访问性；不可迁移项单独列明，不静默跳过。
- **恢复演练**：在另一独立目录恢复 SQLite 与对应文件对象，验证完整性、关键页面和金额结果；记录恢复耗时与允许丢失的数据窗口，避免只检查备份文件存在。
- **首次切换**：如要替代现用系统，另定停写窗口、最后导入与业务入口切换步骤。业务验收通过前保持并行独立试用，不运行两套系统的同步双写。
- **回退**：新系统尚无新增业务写入时，可回到原业务入口；一旦已有新增写入，先保存新记录并确定对账/迁回方案，不能仅切换 URL 就宣布无损回退。代码回退同时核对数据库 schema 兼容性。

资源收益主要来自单进程、本地存储、按需加载、受限缓存与有界任务，TS 编译类型本身不降低运行内存。新领域会增加数据和任务负载，不承诺完整系统始终维持 162 MiB。

实施后分别测量冷启动、稳定空闲、聊天、大文件导入、报告导出和预测重算的 RSS/PSS、CPU、任务峰值、耗时与 WAL 大小。以相同样本和方法比较继承基线与扩展版本。核心服务无需额外常驻中间件；重任务按需执行，完成后释放资源。具体内存门槛在首个闭环实测后确定。

## 工作负载与发布检查

开发基线先限制同时运行的重任务为 1 个，队列持久保存；重任务不阻塞登录、任务进度和普通查询。模型并发与缓存容量在首个闭环测量后设置有限上限，不能使用无限队列或无界缓存。

测量记录固定 Node/SQLite 版本、样本文件大小和行数、数据库/附件规模、模型响应条件及同时请求数。至少覆盖：稳定空闲、典型预算查询、代表性和最大支持导入、报告导出、助手失败降级，以及“一次重任务 + 普通查询”。最大支持文件/行数、空闲/峰值内存和响应时间目标在阶段 2 验收前写成具体值；超限请求需明确拒绝或排队，不依靠 OOM 终止。

每阶段只运行对应改动的有效检查；发布前执行新仓库构建/类型检查、核心财务与权限测试、SQLite 迁移/恢复冒烟及关键页面路径。OCR/模型实测仅针对受影响能力，未验证的外部能力不得标为等价完成。
具体工作负载规模和数值门槛由 OPEN-04 收口。发布回退、库与附件一致恢复按 AC-X07/AC-X08 验收；工具和恢复脚本尚未实现，不能把此规范当成已完成演练。
