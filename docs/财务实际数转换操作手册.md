# 财务实际数转换操作手册

## 首次配置（复核人）

1. 在“财务数据转换 → 数据源与映射审核”新增数据源。`adapter_type` 固定为后端白名单 `fixed_finance_system_v1`，配置只允许 JSON，不执行代码。
2. 配置必须声明工作表、拥有组织范围和拥有科目范围。拥有范围决定完整累计快照的显式零行；相交的数据源会在转换前阻断。
3. 创建映射草稿，下载审核文件，填写组织映射、科目映射和利润表勾稽后导入草稿。
4. 执行“完整检查”。目标必须为映射版本绑定快照中的有效叶子；金额不得映射到数量科目；同优先级规则必须唯一；固定比例权重总和为 `1000000`。已标记 `inactive` 的历史科目规则不参与检查或正式匹配。
5. 复核人点击“审核锁定”。锁定时系统同时固化组织/科目树和报表指标公式；以后主数据结构或指标定义变化不会改写该版本的勾稽口径。锁定版不可再修改；调整必须“复制新版本”后重新审核。

最小配置示例：

```json
{
  "balanceSheetNames": ["科目余额表"],
  "profitSheetNames": ["利润表"],
  "auxiliaryColumns": { "project": ["项目", "辅助项目"] },
  "ownedOrgCodes": ["0101"],
  "ownedAccountCodes": ["I", "C", "E"],
  "amountUnit": "yuan",
  "maxRows": 20000,
  "maxOutputBytes": 10485760
}
```

双层合并表头余额表（如“本年累计/借方、贷方”）配置示例：

```json
{
  "balanceSheetNames": ["Sheet1"],
  "profitSheetNames": ["利润表"],
  "journalSheetNames": ["Sheet1"],
  "balanceLayout": "two_row_cumulative",
  "fixedBookCode": "JIANGYA",
  "fixedOrgCode": "JIANGYA_HOTEL",
  "fixedOrgName": "张家界江垭温泉度假村有限公司",
  "journalCompanyName": "张家界江垭温泉度假村有限公司",
  "journalRequired": true,
  "journalToleranceCents": 0,
  "sourceAccountIncludePrefixes": ["6"],
  "ownedOrgCodes": ["目标组织根编码"],
  "ownedAccountCodes": ["I", "C", "E"],
  "amountUnit": "yuan",
  "maxRows": 30000,
  "maxOutputBytes": 10485760
}
```

双层余额表不含公司和期间列，`fixedBookCode`、`fixedOrgCode`、`fixedOrgName` 必须由复核人按财务系统查询口径固定配置。适配器先验证每个父科目的本年累计借贷都等于直接子科目之和，再只转换末级科目，避免父子重复。`sourceAccountIncludePrefixes` 是显式业务范围；范围外非零末级科目会在报告中计数和留痕，但不参与预算金额，不能用它掩盖范围内未映射科目。

## 月度操作（经办人）

1. 从财务系统导出完整累计余额表，并取得同期间官方利润表；不要手工改金额。
2. 在“月度转换”选择数据源、已锁定映射版本和截止日期，上传余额表、官方利润表；如数据源启用序时簿核验，再上传凭证序时簿 `.xlsx`。
3. 查看文件 SHA-256、解析数量、金额守恒和官方利润表勾稽。任何红色错误都会把批次置为 `blocked`，且没有下载或导入入口。
4. 全部通过后可下载标准文件。点击“创建导入预览”，复核新增、修改、清零数量和来源追溯信息。
5. 点击“人工确认并原子提交”。系统再次调用既有 `parseActualImport` / `resolveActualImport`，并检查预览后拥有范围内是否发生手工修改；冲突时必须重新转换。
6. 如需撤销，在「实际 → 导入批次」执行安全撤销。转换批次、两份原件、映射版本、输出和校验报告永久保留。

## 真实数据并行试运行

1. 完成一个 `validated` 或 `imported` 转换批次后，进入“真实数据并行试运行”。
2. 选择转换批次并上传同期间原手工实际数 Excel。系统只比较该财务数据源拥有范围，范围外手工数据单独计数但不误报差异。
3. 系统按组织编码和预算科目编码逐组合比较整数分，保存原手工文件、SHA-256、净差异、差异绝对值和明细。
4. 零差异由复核人确认后状态为“分毫一致”。存在差异时必须逐项填写原因和处理结论，复核后状态为“差异已解释”。
5. 属于映射问题时复制映射新版本、调整并重新锁定，再创建修订转换批次重跑；最终验收应连续多月达到“分毫一致”。
6. 可下载并行试运行报告和原手工文件，作为财务复核证据。

同数据源同期间重跑必须填写最新成功转换批次 ID 作为修订来源。没有同数据源同年度同截止日成功批次时不得填写修订 ID，其他数据源或期间的批次 ID 也会被拒绝。相同两份原件加相同映射版本已经成功导入时默认拒绝重复。

## CLI

所有 CLI 与 API 共用同一个适配器和 `convert.service.ts`，不包含第二套金额算法：

```bash
cd backend
npx ts-node scripts/inspect-finance-export.ts \
  --file tests/fixtures/finance/balance-2026-06-30.xlsx \
  --journal 凭证序时簿.xlsx \
  --profile PROFILE_CODE --year 2026 --snapshot-date 2026-06-30

npx ts-node scripts/convert-finance-actuals.ts \
  --balance balance.xlsx --profit profit.xlsx --journal 凭证序时簿.xlsx \
  --profile PROFILE_CODE --mapping-version 1 \
  --year 2026 --snapshot-date 2026-06-30 --output actual-import.xlsx

npx ts-node scripts/compare-finance-results.ts \
  --conversion 1 --manual 原手工实际数.xlsx \
  --output 并行试运行报告.xlsx
```

AI 候选是可选的离线审核辅助：

```bash
OPENAI_API_KEY=... OPENAI_MODEL=gpt-5-mini \
npx ts-node scripts/suggest-finance-mappings.ts \
  --balance balance.xlsx --profile PROFILE_CODE \
  --year 2026 --snapshot-date 2026-06-30 --output 待审核候选.xlsx
```

脚本发送给模型的输入对象不含借方、贷方或金额字段；结构化输出会拒绝未知目标编码和每项超过三个候选。生成文件仍须人工审核并导入草稿，再经完整检查和锁定。未配置 API 密钥时只有候选脚本不可用，正式月度转换完全不受影响。

## 固定适配器契约与排错

- 隐藏行不计数；科目名称含“合计/总计”的行不计数；空科目编码行跳过。
- 公式必须有 Excel 缓存计算值，否则阻断。应用公式后需用能保存计算结果的财务软件重新导出。
- 每个数据行的年度、截止日期必须与请求一致；源组织和源科目非零行必须唯一命中。
- 官方报表只提供舍入值时，容差必须在勾稽规则中以“分”明确设置并填写依据；默认容差为 0。
- 序时簿只纳入配置公司、人民币、已过账且位于所选年度截至日内的流水，负数冲销和结转损益照常累计；与余额表任一科目借方或贷方差异超过配置分值即阻断。
- 单层余额表因组织或辅助核算出现相同科目编码多行时，系统先分别累计借贷金额，再与序时簿的同科目汇总值比较。
- 测试样本位于 `backend/tests/fixtures/finance/`，覆盖年初、年中尾差和负数冲销，可用 `npm run fixtures:finance` 确定性重建。
